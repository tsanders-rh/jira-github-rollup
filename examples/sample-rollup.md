# Example: a generated rollup

Illustrative output for a fictional requirement `RHOAIENG-1234`, derived from the
epic linked in [`jira-link-section.md`](jira-link-section.md). All orgs, repos,
issue numbers, and dates are made up.

The skill would show this draft for approval before posting it as a comment.

---

```
h3. Upstream Development Rollup

*Status:* In progress
*Source epic:* example-org/example-gateway#412 — Request routing for tiered models
*Generated:* 2026-10-05

*Summary*
Data-plane routing is merged and the e2e suite is green. The requirement is
blocked on control-plane CRD plumbing in example-controller, which is owned by
another team and has had no activity since 2026-08-28.

*Progress*
2 of 4 child issues closed; 3 pull requests merged.
|| Child || Status || PRs ||
| example-org/example-gateway#413 — request routing | Closed | example-org/example-gateway#520 (merged 2026-09-18) |
```

## What to notice

**The lede is the blocker.** Two of four children are done and three PRs merged,
but the summary leads with what is stuck. A program manager scanning the issue
gets the risk in the first sentence.

**Status is `In progress`, not `Blocked`.** Real work merged recently. `Blocked`
is reserved for cases where nothing can proceed — and it always requires a named
blocker in the Risks section.

**The cross-repo child is called out twice** — once in the table (different repo
than the epic) and once in Risks (different owning team). That dependency is the
single most useful thing in the rollup, and it is exactly what a
single-repo traversal would have missed.

**Open PR age is shown** (`open, 11d`) but merged PRs get a date instead. Age is
a review-latency signal; for merged PRs it is noise.

**No "Since last rollup" section**, because this is the first one. On a later run
the skill would find the marker line at the bottom, diff against this content, and
offer to update this comment in place rather than appending a second near-identical
update.

**No filler.** There is no "No other risks identified" line and no restatement of
the requirement's description. If a section has nothing evidenced to say, it is
omitted.

**Every claim is traceable.** Each status maps to a linked issue or PR a reader
can click. Nothing asserts progress that the links do not support — note that
`#414` lists both of its merged PRs rather than collapsing them into "done."
